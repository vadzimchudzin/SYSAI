# Machine Expert: как устроен файл проекта и как агент создаёт проекты

Записано 10 ноября 2026. Здесь — что выяснено о файле `.project`, почему проект создаёт сам Machine Expert, а не
наш код, и что из этого проверено. Инструменты: `hub/seed/machine-expert` (TOOL.md), `hub/seed/plc-kit`.

## 1. Что разбирали и чем

- **Самого Machine Expert у разработки нет**: это программа для Windows, ставится установщиком Schneider Electric
  (несколько гигабайт, учётная запись). Поэтому двоичные файлы программы (REA, дизассемблер) не разбирались.
- Разобраны **файлы проектов**: Machine Expert построен на CODESYS V3.5, формат `.project` у них общий. Взяты
  открытые проекты CODESYS с GitHub (5 файлов `.project`, архив `.projectarchive`, родной `.export`) и разобраны
  побайтно. Клиентских проектов в репозитории нет.
- Скриптовый интерфейс сверен с опубликованным описанием CODESYS Scripting Engine (ScriptProject, ScriptApplication,
  ScriptOnline, ScriptSystem, ScriptDeviceObject, ScriptTaskConfigObject, ScriptSymbolConfigObject).

Что нужно, чтобы закрыть пробелы: один ПК с Machine Expert (версия), 2–3 своих `.project` и шаблон проекта.

## 2. Файл `.project`

Встречается в двух видах — выбирается настройками проекта при сохранении.

### Открытый контейнер

Обычный ZIP-архив. Внутри:

| Запись | Что это |
|---|---|
| `<guid>.meta` | объект дерева проекта: GUID, родитель, имя, тип, время |
| `<guid>.object` | содержимое объекта (текст POU, настройки задачи, устройство…) |
| `__shared_data_storage_string_table__.auxiliary` | **таблица строк**: каждое имя и каждая строка текста проекта — один раз |
| `__shared_data_storage_schema_table__.auxiliary` | **таблица схем**: для каждого хранимого типа — список полей и их виды |
| `profile.auxiliary`, `*.precompileinfo.auxiliary`, … | профиль (версии компонентов), кэши компиляции |

- **Таблица строк:** число записей, затем записи «номер, длина, текст UTF-8» (числа — varint: 7 бит на байт,
  старший бит — «есть продолжение»). Все остальные части ссылаются на строки по номеру.
- **`.meta`:** 16 байт заголовка (`02 20 09 28` и нули), `u32` длина, байт `0F`, затем varint-номера строк: схема,
  GUID объекта, GUID родителя, имя, свойства, GUID типа, список встроенных типов; в конце 8 байт времени.
- **Типы объектов** (GUID одинаковы в CODESYS и Machine Expert): POU `6f9dac99-8de1-4efc-8465-68ac443b7d08`, список
  переменных `ffbfa93a-b94d-45fc-a329-229860183b1d`, тип данных `2db5746d-d284-4425-9f7f-2663a34b0ebc`, папка
  `738bea1e-99bb-4f04-90bb-a7a567e74e3a`, устройство `225bfe47-7336-4dbc-9419-4105a7c831fa`, приложение
  `639b491f-5557-464c-af91-1471bac9f549`, конфигурация задач `ae1de277-a207-4a28-9efb-456c06bd52f3`, задача
  `98a2708a-9b18-4f31-82ed-a1465b24fa2d`, метод `f8a58466-d7f6-439f-bbb8-d4600e41d099` (полный список —
  `plcproj.TYPES`).
- **`.object`:** тот же заголовок, затем данные по таблице схем: поля идут подряд, строки — номерами из таблицы
  строк, числа — частью varint, частью фиксированной ширины. Текст POU — последовательность записей «строка текста
  (номер в таблице), признак, идентификатор строки (8 байт)». Чтобы читать `.object` целиком, нужно пройти таблицу
  схем; это **не сделано**.

**Что читает `plc-kit`** (`plc_info` на `.project`, модуль `plcproj.py`): вид контейнера и дерево объектов — имена
программ, блоков, списков переменных, задач, устройств и их вложенность. Проверено на 4 открытых проектах: из 172
объектов тип определён у 168, имена и родители — у всех. Текст программ из `.object` не извлекается.

### Закрытый контейнер

16 байт `23 89 ED 33 14 BD 93 4B 8D A9 5D 91 08 C5 32 35`, дальше данные без структуры; длина файла всегда
16 + 16·n — блочный шифр. Это тот же архив, зашифрованный ключом, который хранится в программе. Такой файл без
Machine Expert не читается и нашим кодом не создаётся; ключ не извлекался. `plc_info` называет такой файл закрытым
и отправляет к `me_export`.

**Проекты заказчика** (Machine Expert на CODESYS 3.5.19.40, три проекта M241): все `.project` — в закрытом виде,
первые блоки у всех разные (случайное начало), повторов блоков нет. Рядом с файлом Machine Expert кладёт открытые:
`<имя>.project.OpcUASymbolConf.map` — список переменных, опубликованных в OPC UA, с типом и местом в памяти
(`['GVL.RES_ERR','b','A;1;4;61092;8']`, `['SR_Main.SW_POL_1 (%MW200)','w',…]`); `<имя>.project.settings.conf` —
настройки сервера OPC UA (порт 4840, политики); `<имя>_project.precompilecache` (ZIP) и `*.compileinfo` — имена и
подписи скомпилированных объектов без текста программ. Текст программ из них не достать — только `me_export` или
экспорт из Machine Expert (`.export` заказчика читает plc-kit).

### Архив проекта `.projectarchive`

ZIP: сам `.project`, библиотеки (`*.compiled-library*`), описания устройств, сведения о компиляции, настройки.

## 3. Почему `.project` пишет Machine Expert, а не наш код

Собрать `.project` «по байтам» можно только для открытого контейнера и только пройдя таблицу схем; при этом в файле
есть версии компонентов профиля, описания устройств и кэши, которые программа сверяет при открытии. Ошибка в одном
поле — и проект не откроется или откроется повреждённым. У Machine Expert есть штатный способ делать то же самое —
**скриптовый интерфейс** (Python внутри программы). Через него файл создаёт та же программа, что потом его
открывает, компилирует и загружает в контроллер; закрытый контейнер тоже ей доступен.

Поэтому путь такой:

```
папка ST (пишет агент, проверяет plc-kit)
   │  machine-expert: задание job.json
   ▼
Machine Expert без окна + me_job.py  ──►  Line.project, сообщения компилятора
   │
   ▼
result.json ──► ошибки с файлом .st и строкой ──► агент правит ──► me_update ──► …
```

## 4. Что делает скрипт внутри Machine Expert

| Действие | Вызовы интерфейса |
|---|---|
| новый проект | `projects.create(path)`; контроллер — `device_repository.get_all_devices(имя)` → `project.add(имя, type, id, version)`; либо шаблон: `projects.open(шаблон)` → `save_as` |
| объекты | `create_pou` / `create_program` / `create_function_block` / `create_function`, `create_gvl`, `create_dut`; текст — `textual_declaration.replace`, `textual_implementation.replace` |
| задачи | `create_task_configuration`, `create_task`; `kind_of_task`, `interval`, `interval_unit`, `priority`, `pous.add` |
| OPC UA | `create_symbol_config(True, True, …)`; что публиковать — строка `{attribute 'symbol' := 'readwrite'}` в списке |
| компиляция | `application.build()`; сообщения — `system.get_message_objects(категория)`: текст, номер, объект, место |
| экспорт | `export_xml(…, recursive, declarations_as_plaintext)` или чтение `textual_declaration.text` каждого объекта |
| сеть | `online.gateways[…].perform_network_scan()` |
| контроллер | `set_gateway_and_address` / `set_gateway_and_device_name` / `set_gateway_and_ip_address`, `set_simulation_mode`; `online.create_online_application(app)`: `login`, `start`, `stop`, `read_value`, `set_prepared_value`, `write_prepared_values`, `logout` |

Где у версий интерфейса вызовы различаются, скрипт пробует их по очереди; что не сработало — возвращает в
`warnings`, а не молчит.

## 5. Связь панели и контроллера

Решается до программы (`plc_link`, plc-kit) по моделям из ТЗ:

| Контроллер | Панель | Связь | Что это значит для программы |
|---|---|---|---|
| с сервером OPC UA (TM241CE…, TM251, TM262) | с клиентом OPC UA (Weintek cMT) | **OPC UA** | переменные по именам; списки помечены `{attribute 'symbol' := 'readwrite'}`; адреса не нужны |
| с Ethernet | без OPC UA (Weintek iE / iP / XE / eMT) | **Modbus TCP** | каждой переменной панели — адрес `%M`; панель ведущая |
| без Ethernet (TM241C…) или панель без Ethernet | — | **Modbus RTU** | адреса `%M`; Modbus Manager на Serial Line |

Если в ТЗ связь названа — она и берётся (или инструмент говорит, почему так нельзя). Модели не из таблицы не
угадываются: инструмент возвращает вопросы инженеру.

## 6. Что проверено и что нет

| Что | Состояние |
|---|---|
| Вид контейнера и дерево объектов `.project` | проверено на открытых проектах CODESYS; на проектах Machine Expert — нет |
| Чтение текста программ из `.object` | не сделано (нужен разбор по таблице схем) |
| Закрытый контейнер | не читается; только через Machine Expert |
| Логика `machine-expert` (задание → скрипт → результат → ошибки по файлам) | тесты на подставной программе, 7 тестов |
| Запуск скрипта в настоящем Machine Expert | **не проверено**: нужен ПК с программой |
| Имена программ и ключи запуска (`LogicBuilderShell.exe`, `--runscript`, `--noUI`, `--profile`) | по описанию; переопределяются `SYSAI_ME_EXE`, `SYSAI_ME_CMD` |
| Создание контроллера Schneider без шаблона, конфигурация символов, задачи | по описанию интерфейса CODESYS; на Machine Expert не проверено |
| Вход в контроллер, загрузка | не проверено; на настоящем контроллере — только с `confirm` |

## 7. Первый запуск на ПК с Machine Expert — что проверить

1. `me_find` — программа найдена, версия верная.
2. `me_devices` `{filter: "TM241"}` — скрипт запускается и отвечает. Если «не выполнил скрипт» — взять из ответа
   текст попыток, подобрать команду и задать `SYSAI_ME_CMD`.
3. `me_export` на своём готовом `.project` → папка ST; `plc_info`, `plc_check` по ней.
4. `me_create` из этой папки на шаблоне компании → проект открывается в Machine Expert, компилируется.
5. `me_online` `{simulation: true, read: [...]}`.
6. Записать сюда, что сработало и что нет, с версией Machine Expert.
