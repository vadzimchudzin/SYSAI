# ОПО: от чертежей до проекта ПЛК за 2–4 дня — подробные задачи

Ветка `sysai-agents_OPO` взята от актуального SYSAI (`experimental`). Модуль ОПО — отдельный пакет внутри SYSAI:
вход и люди берутся из SYSAI, ничего существующего не ломается, потом всё вливается в SYSAI без переделок.

## 0. Цель и как мерим

**Цель.** Проект ПЛК (Schneider, языки ST и LD), на который сейчас уходит 1–2 месяца, делается за 2–4 дня вместе
с правками и подгонкой. Рутину делает агент ОПО, люди проверяют и правят.

**Порядок:** сначала извлечение тегов и полный проект ST/LD по стилю компании, потом экраны.

**Как выглядит проект за 2–4 дня:**
- **День 1.** ТО кладёт пакет чертежей → агент за час разбирает его: все входы-выходы и переменные, оборудование,
  вопросы. Инженер ОПО проверяет таблицу тегов (неуверенное подсвечено, есть «показать на чертеже»), вопросы уходят
  в ТО через Telegram.
- **День 2.** Агент генерирует полный проект (ST + LD по стилю компании) и сам собирает его в Machine Expert на
  Windows-компьютере ОПО. Инженер смотрит отчёт сборки и лист «проверить руками».
- **Дни 3–4.** Правки (написал комментарий → агент поправил → пересборка), подгонка, выдача. Экраны — этап 12.

**Метрики** (считаются автоматически на эталонных проектах, ОПО-3.20):

| Что | Цель |
|---|---|
| Найдено каналов ввода-вывода из чертежей | ≥ 99 % |
| Лишних или ошибочных тегов | ≤ 2 % |
| У тега есть источник (файл, лист, место на листе) | 100 % |
| Неуверенное помечено, а не угадано молча | 100 % |
| Проект собирается в Machine Expert с первого раза | ≥ 95 % |
| Проверки стиля компании проходят | 100 % |
| Время инженера на проект среднего размера | 2–4 рабочих дня |
| Расход на нейронки по проекту | в пределах бюджета проекта, отчёт по факту |

## 1. Как устроено

```
ТО ─ чертежи ─▶ Приём ─▶ Разбор (PDF, DWG/DXF, Excel, EPLAN, сканы, ТЗ) ─▶ Теги + оборудование + вопросы
                                                                             │ проверка инженером
                                                                             ▼
   Стиль компании + библиотека типовых ─▶ Генератор ST/LD ─▶ Проверки ─▶ PLCopen XML + привязка каналов
                                                                             │
                   ОПО-воркер на Windows с Machine Expert: импорт и сборка ◀─┘ ─▶ отчёт и проект в SYSAI
```

- **В SYSAI (лёгкая часть, сервер на 512 МБ):** пакет `app/opo/`, таблицы `opo_*`, страницы `/opo/…`, роли,
  очередь задач. Нейронки — через `llm.py` (бюджеты и учёт расходов уже есть), файлы — в S3 через `storage.py`;
  люди, отделы, объекты и клиенты — из SYSAI; уведомления — через бот SYSAI.
- **ОПО-воркер (Windows-компьютер ОПО с Machine Expert):** тяжёлое — DWG→DXF, большие сканы, импорт и сборка в
  Machine Expert. Сам забирает задания у SYSAI по токену, как `speaker-service`; открывать порты не нужно.
- **Экономия токенов:** сначала правила, геометрия листа, таблицы и шаблоны — без нейронок; дешёвая модель — только
  для неясного; сильная — для логики из ТЗ. Результаты кэшируются по хэшу файла и листа: повторный разбор бесплатен.

**Правила совместимости с SYSAI:**
1. Код ОПО — в `app/opo/`, шаблоны — в `app/templates/opo/`, тесты — `tests/test_opo_*.py`, документы — `docs/opo/`.
2. Только новые таблицы с префиксом `opo_`; существующие таблицы SYSAI не меняются.
3. Модуль включается настройкой `opo_on` (по умолчанию выключен): выключенный — SYSAI работает ровно как раньше.
4. В `main.py` — только подключение маршрутов ОПО и пункт меню.
5. Веб-часть — только лёгкие зависимости на чистом Python; тяжёлое — в воркере.
6. Ветка регулярно подтягивает `experimental`; все тесты SYSAI остаются зелёными.

### Этап 1. Вход через SYSAI и уровни доступа

**ОПО-1.1 · Роли** · M · ИИ

Вход — обычным аккаунтом SYSAI. Роль в ОПО:

| Роль | Что может |
|---|---|
| Наблюдатель | видит проекты, к которым допущен; ничего не меняет |
| Технический отдел | загружает чертежи, видит статус своих пакетов, отвечает на вопросы по ним |
| Инженер ОПО | ведёт свои проекты: теги, генерация, сборка, правки |
| Руководитель ОПО | все проекты ОПО; назначает инженеров; утверждает стиль, библиотеку типовых и выдачу |
| Администратор | суперпользователь SYSAI: всё, включая роли и настройки модуля |

- Хранится в `opo_members` (аккаунт → роль → сотрудник SYSAI); суперпользователь SYSAI — всегда администратор.
- Привязка аккаунта к сотруднику SYSAI — для имени, отдела и Telegram.
- **Готово:** матрица «роль × действие» покрыта тестами.

**ОПО-1.2 · Доступ к проекту** · S · ИИ
- Участники проекта: ответственный, инженеры, проверяющие, наблюдатели; ТО видит только свои пакеты.
- Права проверяются на каждом маршруте; ссылки на файлы — короткоживущие и выдаются только после проверки прав.

**ОПО-1.3 · Страница «Люди ОПО»** · S · ИИ
- Аккаунты, роли, сотрудники, отделы. Руководитель ОПО назначает инженеров и наблюдателей, администратор — всех.

**ОПО-1.4 · Своё рабочее место** · S · ИИ
- У каждого своя главная: «Мои проекты», «Ждут моей проверки», «Мои вопросы», «Сборки»; у ТО — «Мои пакеты» и
  вопросы к нему.
- Работает в браузере, в том числе с телефона (просмотр, ответы на вопросы); можно «установить как приложение».

### Этап 2. Приём чертежей от ТО

**ОПО-2.1 · Где лежат чертежи** · S · ОПО + ТО
- В какую базу или папку ТО их скидывает, в какой программе делает (EPLAN, AutoCAD Electrical, Компас-Электрик,
  nanoCAD…), в каком виде (PDF, DWG, DXF, Excel, сканы), как называет файлы и ревизии.
- **Готово:** 2–3 реальных пакета лежат в закрытом хранилище для разработки и тестов.

**ОПО-2.2 · Подключение к базе ТО** · M · ИИ
- Общий порядок для любого источника: «что нового» → «скачать» → «отметить разобранным».
- Делаем тот, что назовёт ТО: папка Google Drive (через `gdrive.py`), Битрикс24 Диск, сетевая папка (через воркер),
  Яндекс Диск (WebDAV) или сама база по её API. Загрузка вручную есть всегда.
- Проверка новых раз в 5 минут; один и тот же файл (по sha256) дважды не разбирается.

**ОПО-2.3 · Загрузка в интерфейсе** · S · ИИ
- Перетаскивание, много файлов, ZIP (с защитой от архивов-бомб и путей `../`), лимит размера пакета (по умолчанию
  200 МБ), прогресс.
- Файлы — в S3 (`opo/<проект>/<пакет>/<sha256>`), в базе — только описание.

**ОПО-2.4 · Пакеты и ревизии** · M · ИИ
- Пакет — набор файлов одной ревизии (А, Б, В…). Новая ревизия → разбор → сравнение с прошлой: что добавлено,
  удалено, изменено. Инженер проверяет только разницу; перегенерируются только затронутые части.
- Проект привязывается к карточке объекта или клиента SYSAI («Объекты и клиенты»).

**ОПО-2.5 · Уведомления** · S · ИИ
- Через бот SYSAI: руководителю ОПО — «новый пакет от ТО» с кнопкой «Назначить»; инженеру — «теги готовы к
  проверке», «сборка прошла / упала»; ТО — вопросы по чертежам, ответ в чате попадает в проект.

### Этап 3. Извлечение тегов — главное

**ОПО-3.1 · Что за файл и лист** · M · ИИ
- Вид файла: PDF с текстом, PDF-скан, DWG, DXF, Excel/CSV, DOCX, выгрузка EPLAN (AutomationML/XML), картинка.
- Класс листа: схема принципиальная (Э3), соединений (Э4), подключения (Э5), обзор ПЛК / карта входов-выходов,
  клеммники, кабельный журнал, перечень элементов (ПЭ3) / спецификация, схема автоматизации, ТЗ / описание
  алгоритма, перечень входов-выходов, прочее.
- Сначала правила: основная надпись (ГОСТ 2.104), шифр документа, ключевые слова; дешёвая модель — только по тексту
  штампа (до 300 токенов) и только если правила не решили.
- **Готово:** ≥ 95 % листов эталонов определены верно; класс правится одним кликом и запоминается.

**ОПО-3.2 · Основная надпись** · S · ИИ
- С каждого листа: обозначение, наименование, лист и листов, ревизия, разработал, проверил, дата.

**ОПО-3.3 · Текст PDF с координатами** · M · ИИ
- Слова с рамками, поворот, шрифт; сборка в строки и колонки; векторные линии — для таблиц и проводов.
- Замер памяти на тяжёлом листе A1: если не укладываемся в 512 МБ сервера — разбор уходит в воркер.

**ОПО-3.4 · Таблицы в PDF (обзор ПЛК, перечни)** · L · ИИ
- Поиск таблиц по линиям и выравниванию; колонки — по словарю синонимов («Адрес», «Канал», «Клемма», «Функция»,
  «Обозначение»…).
- Строка → канал: модуль, слот, канал, адрес, клемма, обозначение устройства, текст функции.
- **Готово:** на эталонах найдено ≥ 99 % каналов обзорных листов.

**ОПО-3.5 · Схемы Э3 в PDF, когда обзора ПЛК нет** · XL · ИИ
- Модули ПЛК на листе — по подписям (`TM3…`, `-A…`, `I0…`, `%IX…`).
- Канал → устройство по проводам: линии листа → граф соединений → устройство (`-SB1`, `-SQ2`, `-KM1`, `-BP1`… по
  ГОСТ 2.710) и его подпись; переходы по ссылкам на другие листы.
- Каждый канал — с рамкой на листе для «показать на чертеже»; неуверенное — в вопросы.

**ОПО-3.6 · DWG и DXF** · L · ИИ
- DWG → DXF на воркере (ODA File Converter, бесплатный).
- DXF → блоки с атрибутами (в AutoCAD Electrical модули ПЛК и устройства несут обозначение, описание и адрес в
  атрибутах), тексты, слои, линии.
- **Готово:** на DXF-эталоне найдены все каналы.

**ОПО-3.7 · Перечни в Excel** · M · ИИ
- Любые листы, объединённые ячейки, несколько таблиц на листе; колонки — по словарю синонимов.
- Неизвестные колонки — дешёвой модели (только заголовок и 3 строки); найденное сопоставление сохраняется как профиль
  формата → в следующий раз без нейронок.

**ОПО-3.8 · EPLAN** · M · ИИ + ТО
- Если ТО работает в EPLAN — попросить выгрузку данных ПЛК в AutomationML и отчёты в Excel: это самый точный
  источник, разбор без нейронок.
- Разбор AutomationML: ПЛК, модули, каналы, адреса, символьные имена, тексты функций.

**ОПО-3.9 · Сканы и фото** · M · ИИ
- Только листы без текста: распознавание моделью со зрением (уже есть в `doctext.py`) по частям листа, кэш по хэшу
  листа; всё найденное — со статусом «проверить».

**ОПО-3.10 · ТЗ и описание алгоритма** · L · ИИ
- Требования к логике: режимы (авто, ручной, местный, дистанционный), блокировки, последовательности, аварии,
  уставки, защиты — каждое с цитатой и номером пункта.
- По разделам; при новой ревизии ТЗ — только изменённые разделы.

**ОПО-3.11 · Схема автоматизации** · M · ИИ
- Позиции приборов (PT-101, TE-102, LSH-103… по ГОСТ 21.208 и ISA 5.1) → величина, диапазон, связь с тегами.

**ОПО-3.12 · Перечень элементов и спецификация** · M · ИИ
- Обозначение → модель устройства → тип сигнала (4–20 мА, 0–10 В, PT100, сухой контакт), диапазон, НО/НЗ — в теги.

**ОПО-3.13 · Сведение источников** · L · ИИ
- Объединение по обозначению устройства и адресу. Конфликты — адрес занят дважды, разные подписи, сигнал не подходит
  модулю, расходятся диапазоны — становятся вопросами с важностью.
- У тега хранятся все источники: файл, лист, место, цитата, способ, уверенность.

**ОПО-3.14 · Модель тега** · M · ИИ
- Поля — в разделе 3. Статусы: черновик → проверить → проверен / отклонён.

**ОПО-3.15 · Имена и описания по стилю** · M · ИИ
- Имя собирается по правилам стиля (ОПО-5.2) из обозначения, функции и типа сигнала; повторы запрещены; описание —
  коротко, по шаблону.

**ОПО-3.16 · Оборудование** · L · ИИ
- Теги группируются в оборудование: двигатель (пуск, работа, авария), частотник, задвижка, клапан, регулирующий
  клапан, аналоговый и дискретный датчик, нагреватель… Сначала по обозначениям и словам, остаток — дешёвой модели
  пачкой.
- Оборудование → типовой объект библиотеки (ОПО-6). Неполный набор сигналов — вопрос: «у М3 нет сигнала аварии —
  так и задумано?»

**ОПО-3.17 · Распределение каналов, если адресов нет** · M · ИИ
- По правилам компании: группировка по шкафам и участкам, резерв (по умолчанию 20 %), подбор модулей → предложение
  состава модулей; это заодно обратная связь для ТО.

**ОПО-3.18 · Проверки качества** · S · ИИ
- Дубли, пустые описания, переполнение модуля, сигнал не того типа, у аналогового нет диапазона и единиц, у важных
  дискретных не указано НО/НЗ, ссылки на несуществующие листы.

**ОПО-3.19 · Бюджет нейронок** · S · ИИ
- Бюджет проекта (по умолчанию $5) и отчёт «что сколько стоило» через учёт расходов SYSAI; при превышении — стоп и
  вопрос руководителю ОПО.

**ОПО-3.20 · Эталоны и автопроверка** · M · ИИ + ОПО
- 3–5 прошлых проектов: входные чертежи + итоговый список тегов из готового проекта → автоматическая проверка
  полноты и точности на каждое изменение разбора.
- **Готово:** метрики раздела 0 считаются в CI на обезличенных копиях.

### Этап 5. Стиль компании

**ОПО-5.1 · Образцы** · S · ОПО
- 3–5 готовых проектов Machine Expert (архив проекта + экспорт PLCopen XML), стандарт ОПО (если записан), шаблон
  проекта компании.

**ОПО-5.2 · Правила стиля** · L · ИИ + ОПО
- Из образцов: имена (префиксы входов и выходов, экземпляров ФБ, программ, GVL, структур), дерево папок проекта,
  шапка POU, язык и вид комментариев, регистр ключевых слов, отступы, порядок вызовов в MAIN, задачи и циклы,
  нумерация аварий, интерфейс для HMI, что пишется на LD, а что на ST.
- Итог: `docs/opo/STYLE.md` для людей + правила в настройках для генератора и проверки; утверждает руководитель ОПО.

**ОПО-5.3 · Редактор стиля** · M · ИИ
- Для руководителя ОПО: правила с живым примером («-BP1 Давление на входе насоса» → имя по правилу), версии стиля;
  проект помнит, по какой версии сделан.

**ОПО-5.4 · Проверка стиля** · M · ИИ
- Проверка ST и PLCopen XML: имена, комментарии, запрещённые конструкции, «магические числа», неиспользуемые
  переменные, каждый вход и выход используется. Работает и для сгенерированного, и для правленного руками кода.

### Этап 6. Библиотека типовых объектов

**ОПО-6.1 · Опись библиотеки ОПО** · S · ОПО + ИИ
- Какие ФБ уже есть (двигатель, частотник, задвижка, клапан, аналоговый вход, ПИД, аварии, режимы…), их входы-выходы
  и где лежат.

**ОПО-6.2 · Описание типового** · M · ИИ
- Для каждого: роли сигналов (обязательные и необязательные), параметры, ФБ и его интерфейс, имя экземпляра, шаблон
  вызова на ST и на LD, испытания; позже — символ для экрана.

**ОПО-6.3 · Недостающие ФБ** · L · ИИ (проверяет ОПО)
- Чего нет — пишу на ST по стилю компании, с испытаниями; у библиотеки есть версии, проект помнит свою.

### Этап 7. Генерация проекта ST/LD

**ОПО-7.1 · Модель проекта** · M · ИИ
- Контроллер, модули, задачи, GVL (входы-выходы, HMI, параметры, аварии), типы (структуры, перечисления), программы
  по участкам, экземпляры ФБ, порядок вызовов, комментарии. У каждого элемента — ссылка на теги и пункты ТЗ.

**ОПО-7.2 · Слой входов-выходов** · M · ИИ
- Переменные с адресами (`AT %IX…`) или привязка в конфигурации модулей — как принято в стиле.
- Обработка входов (инверсия, фильтр дребезга, масштабирование, обрыв 4–20 мА) и запись выходов — отдельными
  программами.

**ОПО-7.3 · Слой оборудования** · S · ИИ
- Экземпляры типовых с параметрами из тегов (диапазоны, уставки аварий).

**ОПО-7.4 · Логика из ТЗ** · XL · ИИ
- Блокировки, последовательности (шаги через CASE), режимы — сильная модель по пунктам ТЗ. Каждый блок — со ссылкой
  на пункт, помечен «проверить», к нему — сценарии испытаний.
- Защиты и аварийный останов — только по явным требованиям, всегда «проверить руками», автоматически не принимаются
  никогда.

**ОПО-7.5 · Аварии и сообщения** · M · ИИ
- Список аварий (номер, текст, приоритет, условие), обработка, квитирование; выгрузка для HMI.

**ОПО-7.6 · Обмен с HMI/SCADA** · M · ИИ
- Структуры команд, состояний и уставок на каждое оборудование; таблица обмена (символы или адреса Modbus — как
  принято).

**ОПО-7.7 · LD** · XL · ИИ
- Где по стилю нужен LD — цепи: контакты последовательно и параллельно, катушки, блоки ФБ; раскладка по сетке,
  перенос длинных цепей, комментарий к каждой цепи; запись в PLCopen XML с координатами.
- **Готово:** LD открывается в Machine Expert и читается как написанный руками (оценивает ОПО).

**ОПО-7.8 · Шаблоны и форматирование** · M · ИИ
- Типовые части — по шаблонам: без нейронок и всегда одинаково; код форматируется по стилю.

**ОПО-7.9 · Перегенерация без потери правок** · L · ИИ
- Ручные правки инженера сохраняются: слияние «прошлая генерация ↔ новая генерация ↔ правленный код»; конфликты
  показываются и решаются в интерфейсе.

**ОПО-7.10 · Версии** · S · ИИ
- Каждая генерация — версия: разница с прошлой, список изменений, кто запустил.

### Этап 8. Schneider Machine Expert

**ОПО-8.1 · Целевая среда** · S · ОПО
- Версия Machine Expert, контроллеры (M241, M251, M262…), модули TM3; или Control Expert (M340, M580) — у него
  другой путь (XEF/XSY). Шаблон проекта компании.

**ОПО-8.2 · PLCopen XML** · L · ИИ
- Выгрузка POU (ST, LD), типов, GVL и папок проекта в PLCopen XML, который Machine Expert импортирует штатно;
  проверка по схеме XSD.
- **Готово:** инженер ОПО импортирует 3 тестовых проекта без ошибок; особенности Machine Expert записаны в
  `docs/opo/MACHINE_EXPERT.md`.

**ОПО-8.3 · Привязка каналов** · M · ИИ + ОПО
- Проверить, что принимает Machine Expert: адреса в GVL или импорт привязки каналов из CSV в редакторе модуля.
  Выбрать путь и сделать выгрузку.

**ОПО-8.4 · ОПО-воркер** · L · ИИ (Windows-компьютер даёт ОПО)
- Папка `opo-worker/`: служба Windows на Python. Сама берёт задания у SYSAI по токену (`X-SYSAI-OPO-Token`),
  скачивает файлы по короткоживущим ссылкам, отдаёт результат; пульс раз в минуту; одна задача за раз; таймауты;
  журнал.
- Установка по инструкции — за 15 минут.

**ОПО-8.5 · Автосборка в Machine Expert** · L · ИИ
- Скриптами Machine Expert (Python, как в CODESYS): открыть шаблон компании → добавить и настроить модули → импорт
  PLCopen XML и каналов → сборка → ошибки и предупреждения в отчёт → сохранить проект и архив проекта.
- Чего не умеют скрипты — автоматизация окон (pywinauto), только для этого шага.

**ОПО-8.6 · Обратный путь** · M · ИИ
- Проект, поправленный инженером в Machine Expert → экспорт PLCopen XML скриптом → разница с генерацией → правки
  сохраняются в SYSAI (ОПО-7.9); частые правки → предложения в стиль и типовые.

**ОПО-8.7 · План Б: свой «Machine Expert»** · M (исследование) · ИИ — только если 8.2–8.6 упрутся
- Разбор формата файла проекта — ограничен по времени (2–3 дня) и только после проверки лицензии Schneider:
  обратная разработка может быть запрещена.
- Путь без разбора формата: свой редактор ST/LD в браузере + проверка открытым компилятором ST; в контроллер всё
  равно загружаем из Machine Expert через PLCopen XML.

### Этап 9. Проверка сгенерированного кода

**ОПО-9.1 · Статические проверки** · M · ИИ
- Схема XSD, стиль, перекрёстные ссылки: каждый тег используется, каждый экземпляр вызывается, ни один выход не
  пишется из двух мест, нет конфликтов адресов.

**ОПО-9.2 · Компиляция без Machine Expert** · M · ИИ
- Сравнить открытые компиляторы и анализаторы ST (ruSTy, MATIEC, iec-checker), выбрать один — для быстрой проверки
  синтаксиса и типов на сервере и в CI ещё до сборки в Machine Expert.

**ОПО-9.3 · Испытания логики** · L · ИИ
- Сценарии «входы во времени → ожидаемые выходы» для типовых и для логики из ТЗ; прогон на компиляторе из 9.2;
  отчёт: что прошло, что упало.

**ОПО-9.4 · Лист проверки инженера** · S · ИИ
- Собирается сам: неуверенные теги, блоки логики от модели, защиты, всё помеченное — со ссылками. Проект не
  выдаётся, пока лист не закрыт.

### Этап 10. Правки и подгонка

**ОПО-10.1 · Правка словами** · M · ИИ
- Комментарий к тегу, блоку или цепи («задержка 5 с на пуск М2») → агент предлагает правку с разницей → инженер
  принимает → пересборка.

**ОПО-10.2 · Учёба на правках** · M · ИИ
- Повторяющиеся правки → предложения в стиль, типовые и словари имён; принимает руководитель ОПО.

### Этап 11. Агент ОПО, нейронки, сеть агентов

**ОПО-11.1 · Выбор модели под задачу** · M · ИИ
- Уровни: дешёвая (классы листов, колонки, описания), средняя (оборудование, ТЗ), сильная (логика, сложные места LD);
  запасные модели при сбое; модели и бюджеты — в настройках ОПО; расход — по проекту.

**ОПО-11.2 · Кэш** · S · ИИ
- По хэшу файла, листа и запроса: повторный разбор того же пакета — без нейронок.

**ОПО-11.3 · Агент ОПО в Telegram** · M · ИИ
- Через бот SYSAI: «что с проектом X?», «сколько тегов не проверено?», «пришли отчёт сборки», «перегенерируй
  участок 2».

**ОПО-11.4 · Карточка A2A** · M · ИИ
- Агент ОПО описан по A2A (навыки: «извлечь теги», «сгенерировать проект», «ответить по проекту») — чтобы потом
  подключиться к общей сети агентов и дирижёру.

**ОПО-11.5 · Граф** · L · ИИ — позже
- Теги, оборудование, требования, код, листы и люди — в граф (Graphiti) для общей памяти сети.

### Этап 12. Экраны — после тегов и кода

**ОПО-12.1 · Целевая панель или SCADA** · S · ОПО
- Vijeo Designer, EcoStruxure Operator Terminal Expert, веб-визуализация Machine Expert или SCADA.

**ОПО-12.2 · Переменные для панели** · M · ИИ
- Выгрузка переменных в формате импорта выбранной программы.

**ОПО-12.3 · Символы типовых** · L · ИИ + ОПО
- Для каждого типового — символ и окно управления в стиле компании.

**ОПО-12.4 · Генерация экранов** · XL · ИИ
- Обзорный экран по схеме автоматизации, экраны участков, аварии, тренды, уставки, пользователи, навигация; разбор
  формата проекта панели или её скрипты.

**ОПО-12.5 · Предпросмотр экранов в браузере** · M · ИИ
- Экраны видны и проверяются в интерфейсе ОПО до выгрузки в программу панели.

### Этап 13. Пилот

**ОПО-13.1 · Замер «как сейчас»** · S · ОПО
- Сколько дней уходит на каждый этап вручную — на 1–2 недавних проектах.

**ОПО-13.2 · Пилотный проект** · L · ОПО + ИИ
- Реальный проект среднего размера целиком через систему: время по этапам, число правок, что мешало.

**ОПО-13.3 · Доводка до 2–4 дней** · L · ИИ
- По итогам пилота — исправления, пока цель не достигнута.

## 5. Что нужно от ОПО и ТО

1. Где ТО хранит чертежи (что за база или папка), в какой программе их делает, 2–3 реальных пакета.
2. 3–5 готовых проектов ОПО: входные чертежи + итоговый проект Machine Expert (+ экспорт PLCopen XML) — эталоны и
   источник стиля.
3. Стандарт ОПО, если записан, и библиотека ФБ.
4. Версия Machine Expert, контроллеры и модули; что принято писать на LD, а что на ST.
5. Windows-компьютер или виртуальная машина с Machine Expert и лицензией — для воркера.
6. Кто в ОПО и ТО и какие у них роли.
7. Можно ли отправлять чертежи заказчиков в облачные нейронки или нужны ограничения.

## 6. Риски

| Риск | Что делаем |
|---|---|
| Чертежи разного качества и в разных форматах | начинаем с самых частых по образцам; неясное — в вопросы, а не догадки |
| В чертежах нет адресов | распределение каналов по правилам компании (ОПО-3.17) |
| Machine Expert не всё импортирует или не всё умеет скриптами | проверяем в первую очередь (8.2, 8.3); запасные пути — 8.5 и 8.7 |
| Логика из ТЗ от нейронки ошибочна | ссылки на пункты ТЗ, испытания, лист проверки; защиты — только руками |
| Сервер SYSAI на 512 МБ | тяжёлое — в воркер |
| Секретность чертежей | ответ на вопрос 7: ограничения по проектам, при необходимости — без облачных моделей |
