# ПЛК: Machine Expert / CODESYS, язык ST

Читает:

- **`.project`** — файл проекта Machine Expert как он есть, в том числе сохранённый «с проверкой целостности» (так
  программа сохраняет по умолчанию; раньше такой файл считался закрытым);
- **`.export`** — «Проект → Экспорт…» (родной экспорт: XML архивированных объектов);
- **PLCopen XML** — «Проект → Экспорт PLCopenXML…»;
- **папку файлов `.st`** — так проект пишет агент (см. ниже).

Пишет: папку `.st`, PLCopen XML и **настоящий `.project`** — из папки ST и шаблона (`plc_project_build`), без
Machine Expert на компьютере.

**Что проверено.** Формат `.project` взят из самой программы (Machine Expert 2.2 = CODESYS 3.5.19.40). Три проекта
ОПО («Родина», «Достоево», «Вульковский рассвет») читаются целиком и записываются обратно байт в байт; программа,
прочитанная из `.project`, совпадает с их же `.export` без единого отличия (49 POU, 11 списков). Проекты, собранные
инструментом на шаблонах всех трёх (новая программа, задачи, список OPC UA, переменные на каналах), открывает и
пересохраняет ядро CODESYS из Machine Expert 2.2 — все объекты прочитаны, сообщения те же, что у исходных проектов.
Объекты, которые инструмент создаёт сам, совпадают с теми, что создаёт ядро, поле в поле.

**Не проверено:** открытие в самом окне Machine Expert и компиляция — ядро запускалось без оболочки Schneider
(ей нужна лицензия), библиотек и репозитория устройств. Первый собранный проект откройте в Machine Expert при
инженере и скомпилируйте; что скажет программа — запишите в `docs/opo/MACHINE_EXPERT.md`. Импорт собранного PLCopen
XML в Machine Expert тоже не проверен.

## Когда применять

- Разобрать присланный проект ПЛК: что за программы и блоки, какие переменные, какие адреса видит панель.
- Найти ошибки до Machine Expert: незакрытые блоки, необъявленные имена, пересечения адресов.
- Снять стиль готового проекта, чтобы следующий делать так же (`plc_style`).
- Написать программу с нуля по документации: файлы `.st` → `plc_check` → `plc_project_build` → файл `.project`.
- Достать программу из готового `.project` (в том числе LD: объявления и имена) — без Machine Expert.
- Посмотреть, какие переменные стоят на каналах контроллера и модулей, и расставить свои (`plc_io`, `plc_io_map`).
- Дать панели теги: `plc_hmi_tags` — адреса Modbus или имена OPC UA для привязки объектов экранов (ebpro-cmtp).
- Перед программой решить связь панели и контроллера: `plc_link` по моделям из ТЗ.
- Вести проект «под ключ» по этапам: `plc_stage_update` (окно «Агент SYSAI» показывает их полосой).

## Как запускать

Синхронизатор ставит папку в `%SYSAI_HOME%\tools\plc-kit` и запускает `python server.py` на своём Python (только
стандартная библиотека, ничего не скачивается, в сеть инструмент не ходит: адреса `plcopen.org`, `w3.org` и
`3s-software.com` в коде — имена пространств XML, а не подключения). Доступ к папкам проверяет SYSAI: `plc_export_st`,
`plc_build`, `plc_project_build`, `plc_project_template`, `plc_io_map` и `out_file` у `plc_hmi_tags` и `plc_style` пишут
файлы — в папку, открытую агенту на запись. Файл `.project` с проверкой целостности открывается за несколько
секунд (шифр считается на чистом Python; с пакетом `cryptography` — мгновенно).

**Таблицы — страницами.** `plc_variables`, `plc_hmi_tags`, `plc_io` и `plc_check` отвечают страницей (по умолчанию
200 строк; `limit`, `offset`) и говорят, сколько всего (`count`) и откуда брать дальше (`next_offset`). Ответ остаётся
в разговоре и оплачивается с каждым следующим запросом, поэтому нужное ищут через `filter`, `scope`, `device`, а всю
таблицу тегов берут файлом (`out_file` у `plc_hmi_tags`). `plc_check` — сначала ошибки.

Разбор: `plc_info` → `plc_pous` → `plc_pou` (нужные) → `plc_variables` / `plc_addresses` → `plc_check` → `plc_style`.
Сборка: папка `.st` → `plc_check` → `plc_project_build` (файл `.project`) или `plc_build` (PLCopen XML для импорта).

## Адреса и Modbus

Область `%M` контроллера — она же таблица регистров Modbus (holding): `%MW n` — регистр `n`.

- **Биты по байтам** (Schneider M241): `%MX a.b`, бит 0..7 байта `a` — это бит `(a mod 2) · 8 + b` регистра `a div 2`.
  `%MX1.2` — регистр 0, бит 10. Слово `%MW0` и биты `%MX0.x`, `%MX1.x` — одна и та же память.
- **Биты по словам** (ONI и подобные): `%MX a.b`, бит 0..15 слова `a` — бит `b` регистра `a`. Инструмент понимает это
  сам: если в проекте есть `%MX…​.8`–`.15`, биты считаются по словам.
- `%MD n` — регистры `2n` и `2n+1`. REAL и DINT занимают два регистра.
- У Weintek регистры считаются с единицы: `4x` 1 — это регистр 0; бит — `4x_Bit`, регистр и две цифры бита
  (`4x_Bit 100` — регистр 0, бит 0; `4x_Bit 110` — регистр 0, бит 10).

`plc_addresses` называет пересечения: один адрес у двух переменных (предупреждение — так делают нарочно для кнопки и
её выхода) и слово поверх битов того же регистра (ошибка).

## Связь панели и контроллера

`plc_link` `{controller, panel}` или `{text: «текст ТЗ»}` (модели и слова о связи будут найдены в тексте), `wish` —
связь, названная заказчиком.

- Оба устройства умеют OPC UA (TM241CE…, TM251, TM262 и Weintek cMT) → **OPC UA**: переменные по именам, адреса не
  нужны. В `project.json`: `"link": {"kind": "opcua", "lists": ["GVL"]}`; в начале списка — строка
  `{attribute 'symbol' := 'readwrite'}` (без неё `plc_check` предупредит). `plc_hmi_tags` даёт теги `GVL.Имя` простых
  типов; экземпляры блоков и структуры в теги не идут.
- Контроллеры **M241 / M251** называют переменные на своём сервере OPC UA номерами: `ns=2;i=N`, где N — CRC-32
  имени «Список.Переменная» без последней инверсии (сверено на 582 тегах настоящего проекта панели). `plc_hmi_tags`
  даёт этот номер в поле `node_m241`; `cmtp_edit` `add_tags` (ebpro-cmtp) считает его сам, когда в таблице панели
  теги с номерами. Типы для панели — в `add_tags`: WORD → UINT, DWORD → UDINT, BYTE → USINT.
- **Сверка экранов с программой:** `plc_tag_check` `{path, tags}` — `tags` из `cmtp_tags` (или имена, взятые из
  `cmtp_objects`): `missing` — тег есть на экране, а переменной в программе нет (на панели объект работать не
  будет); `type` — тип другой; `node` — номер узла не тот, что у этого имени; `not_plain` — это блок или структура.
  На готовом проекте заказчика сверка нашла 3 таких тега из 475.
- Панель без OPC UA (Weintek iE / iP / XE / eMT) или так просит ТЗ → **Modbus TCP**: `"link": {"kind": "modbus_tcp"}`,
  адреса `%M`. Нет Ethernet у одного из устройств → **Modbus RTU**.
- Модель не из таблицы инструмента или ТЗ противоречит возможностям — `link` пустой, в `ask` вопросы инженеру.
  Разрешение панели — из таблицы серий; сверить при создании проекта панели в EasyBuilder Pro.

## Этапы проекта

`plc_stage_update` `{project_dir, stage, state, note, facts}` пишет `pipeline.json` в папке проекта: этап `work` /
`done` / `problem` / `todo` и короткая заметка; `facts` — решения (`controller`, `panel`, `resolution`, `link`,
`style`) и итоги (`machine_expert`, `project_file`, `hmi_file`, `doc_file`). Этап не закрывается раньше предыдущих
(экраны и документы — можно без компиляции: её может сделать инженер). Только `project_dir` — прочитать ход.
В папках результата лежит только результат: `plc/` — `.project`, `hmi/` — проект панели, `docs/` — `.docx`. Всё
остальное (исходники `.st`, шаблоны, таблицы, скрипты, заметки) — в `_work/`; закрывая этап, инструмент называет
лишние файлы (`extra`), их переносят в `_work/`. Служебные файлы Machine Expert и EasyBuilder рядом с проектом (`.~u`,
`.opt`, `.precompilecache`, `.bootinfo`, `.compileinfo`, `.backup`, `.bak`) лишними не считаются — их не трогают.

## Папка ST — как пишут проект с нуля

```
project.json      {"name": "Line1", "controller": "TM241CE40R", "panel": "cMT3072X",
                   "link": {"kind": "opcua", "lists": ["GVL"]},
                   "tasks": [{"name": "MAST", "interval": "20ms", "priority": 15, "pous": ["BIND", "Main"]}]}
GVL.st            VAR_GLOBAL … END_VAR                      — список глобальных переменных, их может быть несколько
In_Out.st         VAR_GLOBAL … END_VAR                      — входы и выходы модулей
Noria_class.st    FUNCTION_BLOCK Noria_class  VAR_INPUT … END_VAR  VAR_OUTPUT … END_VAR  VAR … END_VAR  <код>
Main.st           PROGRAM Main  VAR … END_VAR  <код>
Motor.st          TYPE Motor : STRUCT … END_STRUCT END_TYPE — тип данных
```

Файл узнаётся по первому слову; у POU код — всё после объявления (заголовок и блоки `VAR … END_VAR` подряд). Имя
объекта — имя файла (латиница, цифры, `_`). Кодировка UTF-8.

Порядок: `plc_export_st` на готовом проекте того же стиля (пример перед глазами) → написать файлы → `plc_check` →
исправить → `plc_build` → отдать XML инженеру. `plc_build` не пишет файл, пока `plc_check` находит ошибки
(`force` — записать черновик XML); `plc_project_build` с ошибками проверки файл `.project` не пишет никогда.

**Что проверка считает ошибкой** (компилятор Machine Expert откажет наверняка): незакрытые блоки и скобки, незакрытый
комментарий или строка, операторы из C (`&&`, `||`, `!=`, `==`, `!`, `+=`), время не по IEC (`T#90sec`),
преобразование, которого нет (`INT_TO_FLOAT`), `VAR` / `END_PROGRAM` / `METHOD` посреди кода, имя переменной, занятое
языком, повторное объявление, неверный адрес, задача вызывает блок или функцию вместо программы, приоритет не 0–31,
период не как `20ms`. Имя, которого нет в проекте, — предупреждение: оно может быть из библиотеки.

## Файл `.project`: новый проект без Machine Expert

```
_work/st/               папка ST: project.json + *.st         (пишет агент, проверяет plc_check)
materials/Старый.project  готовый проект с тем же контроллером  (или шаблон компании)
_work/templates/        шаблон без программы                  (plc_project_template)
plc/Line.project        новый проект — единственный файл в plc/ (plc_project_build)
```

1. **Шаблон.** Устройства (контроллер, модули TM3, сеть, библиотеки) в файле описаны данными репозитория устройств
   Machine Expert — на компьютере без программы их взять неоткуда. Поэтому новый проект делается из шаблона: любого
   `.project` с тем же контроллером и нужными модулями. `plc_project_template` `{path, out_file}` вынимает из
   готового проекта программу и оставляет устройства, библиотеки, конфигурацию задач и настройки. Можно дать
   `plc_project_build` и сам готовый проект — программа вынимается так же.
2. **Каналы.** `plc_io` `{path: шаблон}` — что стоит на входах и выходах: `Application.x0_0` — переменная программы
   (её нужно объявить в новой программе под этим именем — в списке без `{attribute 'qualified_only'}`), запись с
   `new_variable` — переменную объявляет сама привязка (`idwDI_IDW0`), объявлять её не нужно. Другие имена —
   `plc_io_map` `{path, out_file, changes: [{device: "DI", channel: "I0", variable: "Start_1"}]}`.
   **Шаблон хранит на каналах переменные своей прежней программы.** Канал с переменной, которой в новой программе
   нет, Machine Expert не скомпилирует. Три выхода: объявить эти переменные; шаблон со свободными каналами —
   `plc_project_template` `{clear_io: true}`; снять лишнее при сборке — `plc_project_build` `{io: "drop_undeclared"}`
   (`clear` — снять все).
3. **Сборка.** `plc_project_build` `{src_dir, template_file, out_file}`: типы → списки → функции → блоки → программы
   в «Application» контроллера; задачи из `project.json` (период, приоритет, программы; задачи шаблона, которых
   нет в `project.json`, убираются); при `"link": {"kind": "opcua"}` — список переменных, которые публикует
   контроллер (простые типы из списков `lists`). Файл сохраняется как у Machine Expert — с проверкой целостности.
   После записи файл читается обратно и сверяется с папкой: «сходится» или список отличий. Каналы сверяются с
   программой: сколько занято и свободно; «ОШИБКА привязок» — каналы, называющие переменные, которых в программе
   нет (ответ — ошибка, хотя файл записан: его нужно исправить до компиляции); одна переменная на двух каналах;
   битовый канал с небитовой переменной и наоборот.
4. **Правки.** Изменил `.st` → `plc_project_build` `{src_dir, out_file}` без шаблона: объекты сопоставляются по
   именам, изменённые получают новый текст (объект остаётся тем же), новые добавляются, остальное в проекте —
   устройства, настройки, объекты, которых нет в папке, — не трогается; такие объекты названы в ответе.
5. **Компиляция** — в Machine Expert: инженер открывает файл, либо инструмент machine-expert (`me_build`) возвращает
   ошибки компилятора с файлом `.st` и строкой → исправить `.st` → пункт 4 → снова.

Устройства инструмент не добавляет и не убирает: другой набор модулей — другой шаблон или правка в Machine Expert.

## Ограничения

- Графические языки (LD, FBD, CFC): читаются объявления и имена, которые встречаются в схеме; код не читается, в
  XML и в `.project` не пишется (графические POU шаблона при `keep_program` остаются как есть).
- `plc_check` — не компилятор: типы выражений, вызовы библиотек и конфигурацию модулей проверяет Machine Expert.
- Конфигурация устройств (модули, Modbus-ведомый, сеть) не создаётся: она приходит из шаблона.
- Методы и действия блоков читаются из `.project` и `.export` и пишутся в `.project`, когда есть в модели; в папку
  ST и XML пока не раскладываются. Свойства блоков не пишутся.
- `.project` с паролем или ключом (шифрование проекта, а не проверка целостности) не читается — такой файл открывает
  только Machine Expert.
- Кэши компиляции в файле (`*.precompileinfo`) после правки убираются: Machine Expert строит их заново при открытии.

## Ошибки

- «не файл проекта Machine Expert / CODESYS» / «файл проекта не разобран» — это не `.project`, он повреждён или защищён
  паролем; такой файл открывает Machine Expert (machine-expert: `me_export`).
- «Файла … нет: для нового проекта назовите template_file» — `plc_project_build` без шаблона обновляет существующий
  проект; для нового нужен шаблон.
- «в проекте нет «Конфигурации задач»» / «нет объекта OPC UA Symbol Configuration» — в шаблоне нет контроллера или
  его сервер OPC UA не настроен: возьмите другой шаблон или добавьте в Machine Expert.
- «объект … в проекте написан не на ST» — в проекте есть объект с тем же именем на LD / FBD / CFC.
- «Сверка с папкой после записи: …» с отличиями — файл записан не так, как просили: не отдавайте его, сообщите.
- «этап нельзя закрыть раньше предыдущих» — сначала закрой названные этапы (или отметь `problem`).
- «не экспорт Machine Expert и не PLCopen XML» — это другой XML; проверь, что файл сохранён командой экспорта.
- «нет POU …» — такого имени нет: список в `plc_pous`.
- «файл ST должен начинаться с PROGRAM, FUNCTION_BLOCK, FUNCTION, TYPE или VAR_GLOBAL» — в папке лежит `.st` без
  заголовка; имя файла названо в ошибке.
- «объект … уже есть в …» — два файла с одним именем объекта (имена ПЛК не различают регистр).
- «Проверка нашла ошибки, файл не записан» — `plc_build` перечисляет их; исправь или собери черновик с `force`.
- «имя … нигде не объявлено» — предупреждение: переменная не объявлена или это функция библиотеки (`INT_TO_REAL`,
  пространство `plc_gvl`) — такие Machine Expert знает сам.
